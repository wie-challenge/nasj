No P0 data loss, unauthorized payment or liability erasure was reproduced. These three P1 findings prevent unconditional acceptance.

## A12-01 — Legacy closure bypasses an unresolved financial adjustment

- **Severity:** P1
- **Story:** E10-14 / #73, criteria 1–3 and 5
- **Affected file/function:** `apps/api/src/modules/commerce/commerce.service.ts:829`, `CommerceService.orderAction`; compare `FinanceService.assess` in `apps/api/src/modules/finance/finance.service.ts`.
- **Reproduction:** Prepare an otherwise settled synthetic legacy order with one QA-approved/delivered piece and matching simulated buyer/artisan payments. Add a valid `FinancialAdjustment` in `PENDING_REVIEW`. `GET /api/v1/finance/orders/:id/closure` returns blockers including `SETTLEMENT_POLICY_REVIEW_REQUIRED`. Submit `POST /api/v1/commerce/orders/:id/actions` with `{next:"CLOSED",version:1,materialsResolved:true,dispositionNote:"Synthetic disposition does not resolve the adjustment"}` as its authorized finance/operator actor.
- **Expected behavior:** Every close route denies an unresolved adjustment or disposition until the authoritative checklist and approved policy allow closure. Synthetic payments do not override that checklist.
- **Observed behavior:** HTTP **201**, order becomes **CLOSED**, and the adjustment remains **PENDING_REVIEW**. The guard checks payables, deposits, payment disputes, linked catalogue projection and FinanceRecordEvent rows whose `orderId` is populated; it omits FinancialAdjustment and inventory sources. Earlier finance events usually identify a target rather than populate the new optional `orderId`, so their presence cannot reliably supply this missing guard. The separate closure endpoint remains conservative, but it is bypassed here. No liability was erased in the reproduction; the closed-order representation is wrong.
- **Evidence:** [Independent result `LEGACY_ADJUSTMENT_CLOSE`](../../../../engineering/audits/batch12/evidence/independent-results.json); [reproduction source](../../../../engineering/audits/batch12/evidence/independent-checks.ts); [executed log](../../../../engineering/audits/batch12/evidence/targeted-final.log). The original regression covers a direct FinanceRecordEvent bypass case, not this adjustment case.
- **Recommended fix:** Make every close transition invoke the same transaction-bound financial readiness authority. Include all adjustment, inventory, sample, obligation and dispute sources by their actual relationships, not a partial list or the new optional event annotation. Preserve pure synthetic legacy regression behavior only where no authoritative obligations or unresolved dispositions exist. Add this HTTP counterexample as a denial test; do not invent a lawful exception or remove liabilities.

## A12-02 — Contract acceptance can occur before required finance review

- **Severity:** P1
- **Story:** E18-03 / #206, criterion 5
- **Affected file/function:** `apps/api/src/modules/procurement/procurement.service.ts:1095`, `ProcurementService.accept`; `apps/api/src/modules/sales/sales.service.ts:400`, `SalesService.propose`.
- **Reproduction:** Create an authorized prospect and draft pilot proposal; revise it to SENT with its valid RFQ reference. Use an otherwise valid, costed quote for that buyer/operator. Confirm there are zero `RfqFinanceReview` events for the RFQ, then have the authorized buyer accept the exact quote through `POST /api/v1/procurement/rfqs/:id/accept`. In a separate follow-up, first record an authorized finance decision **HOLD / UNFUNDED** for that exact quote, then attempt the same acceptance.
- **Expected behavior:** Finance review of the exact quote and funding plan precedes the new sales-linked commitment, independently of when a salesperson records WON.
- **Observed behavior:** HTTP **201**, a commercial order and procurement acceptance are created with **zero finance reviews**. The follow-up also returned **201** despite an explicit **HOLD / UNFUNDED** review. The proposal API accepts an RFQ reference on SENT but persists the relational `rfqId` only when status is WON. Acceptance requires review only if it finds that relational proposal link. Recording a win later therefore makes the review gate too late. This is an authorized buyer action that bypasses a required financial control; it does not create an artisan commitment or claim a legal signature.
- **Evidence:** [Independent result `FUNDING_BEFORE_WON`](../../../../engineering/audits/batch12/evidence/independent-results.json); [explicit unfunded hold result](../../../../engineering/audits/batch12/evidence/funding-hold-results.json) and [executed hold probe](../../../../engineering/audits/batch12/evidence/funding-hold.log); [reproduction source](../../../../engineering/audits/batch12/evidence/independent-checks.ts); [executed log](../../../../engineering/audits/batch12/evidence/targeted-final.log). Existing tests mark WON before testing acceptance, so they miss the reverse ordering.
- **Recommended fix:** Establish and authorize RFQ/proposal linkage before acceptance, independent of win/loss outcome. Enforce the applicable finance gate at the commitment authority for every in-scope contract. Keep review tied to the exact current quote/cost/funding evidence and test both conversion orderings. A salesperson changing pipeline status must not enable or disable a financial control.

## A12-03 — Verified timeliness is implemented only as an unreachable projection branch

- **Severity:** P1 (acceptance violation; no false verified payment was produced)
- **Story:** E10-13 / #148, criteria 1–4
- **Affected file/function:** `apps/api/src/modules/finance/finance.service.ts:987`, `FinanceService.timeliness`; `apps/api/src/modules/finance/analysis.ts:72`; `apps/api/prisma/migrations/20261027080000_financial_controls/migration.sql:107`.
- **Reproduction:** Inspect the native `PayoutExecutionRecord` CHECK constraints after normal migration. `execution_unverified` requires `bankVerified=false` and status `VERIFICATION_PENDING` or `FAILED`. Inspect the report adapter: its positive denominator requires `bankVerified=true` and `VERIFIED_SETTLED`. Normal payable writers copy free-text payment conditions or sample terms without a structured contractual `paymentDueAt`; the report only looks for that JSON field. Exercise the current authenticated report and the pure function separately.
- **Expected behavior:** Verified on-time/late figures must be reproducible through supported immutable contractual dates and legitimate settlement evidence, with pending/failed/planned states identifiable. Unknowns should stay unavailable until such evidence exists.
- **Observed behavior:** The pure function computes the requested cases correctly for manually constructed verified inputs, but **no schema-valid current execution row can enter that positive path**. The authenticated tests demonstrate only zero eligible/unknown reporting. Existing arbitrary payment-conditions text is not a structured due-date workflow. Pending and failed execution details are collapsed into unknown output. Consequently the VERIFIED story classification is unsupported; the safe negative path is implemented, while the positive integration remains incomplete.
- **Evidence:** [Native constraint record `TIMELINESS_REACHABILITY` and eleven-case `TIMELINESS_PURE`](../../../../engineering/audits/batch12/evidence/independent-results.json); [additional exact financial checks](../../../../engineering/audits/batch12/evidence/pure-finance.json); `apps/api/src/modules/procurement/logistics.ts:1022`; `apps/api/src/modules/finance/sample-obligations.ts:35`.
- **Recommended fix:** Classify the story PARTIALLY_IMPLEMENTED until an approved verification policy and supported immutable due-date/settlement path exist. Then exercise on-time, late, partial, failed, disputed and overpaid cases through the real service and PostgreSQL. Do not weaken the current anti-fabrication SQL constraint or turn simulated transfers into verified payments merely to make a positive test pass.
