# Security model and residual risks

Nest independently enforces Better Auth sessions, active verified accounts, privileged MFA, CSRF, approved origin/JSON, strict Zod contracts, bounded lists and durable rate limits. Frontend roles/hidden buttons never grant access. Organization permissions derive from current membership/approval. Artisan assistance remains explicitly consent/scoped; global ADMIN alone does not grant organization or artisan access.

Commerce uses actual current BUYER membership in the owning approved buyer organization and specific operational roles in its assigned approved INTERNAL organization. Only the owning artisan accepts/declines or reports progress. QA cannot approve payments; buyers cannot read individual offers/payouts; artisans cannot read buyer quotes/receipts; unsubmitted RFQ drafts stay private. Client-substituted tenant/object/batch IDs do not bypass these checks. Six related tables enforce immutable synthetic provenance and bounded/reconciled rows. The API does not support live contracts or transfers.

Capacity and commerce command outcomes bind actor, resolved resource, operation and canonical payload. Commerce requires an idempotency key and optimistic version; current authorization/consent checks precede replay. Existing unkeyed capacity calls still intentionally create revisions. All commerce state/count/money decisions invoke pure rules inside the shared IAM transaction/lock order. State, audit, outcome and metadata event commit together. External invitation/support SMTP is not covered by the internal local receipt consumer guarantee.

Outbox events allow only IDs/types/actor/tenant/correlation/version/timestamps, with no snapshot/reason/specification/term/payment/sensor payload. IDs and private outcomes remain personal metadata requiring restricted access and retention review. There is no monitoring ingestion or commercial ETL. Strict schema rejection demonstrates explicit-field exclusion, not semantic detection of sensitive information entered into permitted free text. No medical efficacy or complete privacy-compliance claim is made.

Deployment still needs least-privilege DB grants, reviewed retention/outcome expiry, encrypted off-site backup storage, operator-approved RPO/RTO, ingress/TLS/proxy trust and hosted alert routing. Conservative prototype branches block unresolved disputes/amendments/partial-fulfillment remedies rather than erasing liabilities. No real bank/provider adapter, independent penetration test or complete accessibility certification is supplied. See the [security execution report](../99-archive/historical-audits/e16-security-test-report.md) and [commerce architecture](../02-architecture/commerce-domain.md).


The commerce report and CSV endpoints recheck approved current resource memberships/roles inside the same IAM transaction as the read. Buyer output omits artisan private earnings; non-finance internal roles receive fulfillment only. Whole-order analytics is denied to artisans and unrelated buyers. Inbox scopes are derived from current memberships and artisan account identity, and revocation hides prior organization notices. No public rebuild/queue/backup route exists. CSV uses fixed names/enums and integers, avoiding untrusted spreadsheet formulas. Automated integration tests cover these reads, downloads and revocation.

Database-local consumers write derived projections/notices/receipts atomically; actual process termination and rollback/recovery are tested. No SMTP call occurs inside those transactions. The independent simulator has no API, database or network dependency; its fixture lifecycle makes zero attempted fetch/TCP calls and cannot alter commercial/capacity records. Physical network non-upload remains pending hardware. Backups use authenticated AES-256-GCM with private owned key/archive paths; tampering/permission/symlink/overwrite/retention failures and actual logger redaction are tested. Retain and recover encryption keys separately from archives.
